# NPK 这套打包方式，放在今天还必要吗？

> 写作日期：2026-11-05。前半部分的所有数字都是本次在
> `/mnt/e/dnf-sf/sf115/人造神客户端/ImagePacks2/`（4,730 个 `.NPK`，28.5 GB）上实测出来的，
> 复现命令见文末；后半部分的现代方案属于**行业实践**，不是本机实测。
> 逐字节格式本身见 [`docs/NPK-FRAME-BYTES.md`](NPK-FRAME-BYTES.md)。

---

## 0. 结论先说

| 问题 | 回答 |
| --- | --- |
| 这套格式还能用吗？ | **能，而且磁盘效率意外地好**：实测 zlib 后只占原始像素体积的 **8.5%**（335 GB → 28.5 GB） |
| 按今天的行业标准算「有必要」吗？ | **作为运行时容器：够用；作为内容管线 / 热更体系：已经过时** |
| 过时的根源是什么？ | 不是 magic、不是 XOR，而是它把三件事锁死成一件：**包 = 索引 + 数据**、**条目 = 补丁单元**、**帧 = 压缩单元 = 纹理** |
| 一句话建议 | **别重做格式，改粒度。** 优先 atlas 合批 → VRAM 压缩格式 → 补丁 chunk 化 → 索引瘦身 |

---

## 1. 它当年为什么这么设计（不是设计失误）

2005 年的约束条件：DVD/单机安装、机械硬盘、DirectX 9、纯 2D 精灵、没有 CDN、没有引擎 pak 系统、
内存以百 MB 计。在这个前提下，NPK 的每个选择都是**当时的最优解**：

| 设计 | 当年解决什么 |
| --- | --- |
| 索引全部放在文件头、定长 264B | 打开包 = 一次 seek 读完索引，之后任意条目 O(1) 定位；不需要遍历 |
| 每个 `.img` 是独立完整文件 | 单条目损坏不牵连全包；打包器只管拼接；解包器不用懂依赖 |
| 每一帧单独 zlib | 只解当前帧，内存占用与动画长度无关 |
| ARGB8888 / 1555 原始像素 | DX9 时代 GPU 不普及块压缩，CPU 解压后直接 `LockRect` 上传 |
| SHA-256 校验 + 名字 XOR | 防下载损坏、挡一下「随便改图」的玩家 |

**这些都没错。** 过时的是它们的**组合方式**在 20 年后要付的账。

## 2. 实测：今天要付的代价

### 2.1 索引：55.8 MB，其中 73% 是零

| 项 | 实测值 |
| --- | --- |
| 全语料条目数 | 211,456 |
| 索引占用 `211,456 × 264B` | **55.8 MB** |
| 其中文件名槽位固定 256B，实测名字长度 **中位 64B / 最大 112B** | 每条约 **192B 是零填充** → 约 **40.6 MB 纯浪费** |
| 换成现代 TOC（8B hash + 8B offset + 4B size + 变长名字池） | 约 **17 MB**（≈1/3） |

影响不只是体积：264B 定长意味着**每条记录都要在内存里铺开**，而现代做法是排序后的 hash 表 + 字符串池，
可以二分 / mmap 直接查，不必全量解析。

### 2.2 压缩：2880 万个独立 zlib 流

| 项 | 实测值 |
| --- | --- |
| 帧总数（剔除坏头） | 28,777,699 |
| 其中 zlib 压缩的帧 | **99.83%**（抽样 423,483 帧中 422,751） |
| 平均每帧压缩后 | **991 字节** |
| 独立 zlib 流的固定头开销（约 6B/流） | ≈ **173 MB**（占 28.5 GB 的 0.6%） |
| 原始像素总量（解压后） | ≈ **335 GB** → 压缩率 **8.5%** |

0.6% 的头部开销不算事，真正的问题是**数量级**：加载一段动画要发起上百次 `inflate`，
每次都是「分配 + 解压 + 通道重排 + 上传」。而且因为流太碎，**用不了共享字典**——
现代 zstd 对 1KB 级小块的字典训练通常还能再省 10–20%，这里吃不到。

### 2.3 像素格式：96.7% 的帧是未压缩 ARGB8888（4B/px）

| 项 | 实测值 |
| --- | --- |
| `0x10` ARGB8888 占帧数 | **96.7%**（27,829,633 / 28.77M） |
| 解压后像素总量 | ≈ 335 GB |
| 若换成 BC7 / ASTC 4×4（1B/px） | 原始体积 ÷4 → **VRAM 占用 ÷4**，且 GPU 可直接采样 |

**但要注意一个反直觉点**（见 §4）：这 8.5% 的压缩率之所以这么漂亮，是因为精灵帧里大片透明像素
被 zlib 吃掉了。换成 BC7 会把这些「长零串」打散成熵很高的块，**磁盘体积可能反而上升**。
所以 BCn 的收益在**显存和加载路径**，不在下载体积。

### 2.4 补丁粒度：改一帧 = 重下整张图；实际已经演化成「整包重发」

| 项 | 实测值 |
| --- | --- |
| 平均每个条目（`.img`） | **134.9 KB / 136 帧** |
| 平均每帧压缩后 | 991 B |
| 改一帧的最小补丁单元 | **整个 `.img`**（平均 135 KB，大的动画 img 可达数十 MB） |
| 以 `!` 开头的补丁包（靠文件名 `!` 抢加载优先级） | **156 个 / 3.8 GB** |
| 字节完全相同的重复包 | **17 组 / 0.3 GB**（例：`!    卢克.NPK` 与 `!!!…卢克.NPK` 各 256.5 MB） |
| 同名 img 在多个包里出现（补丁包带完整副本、原包副本还在） | **7,527 个名字 / 冗余 1.88 GB（占 6.7%）** |

**这一段是最能说明问题的**：因为容器没有「同一资源的多个版本 + 优先级清单」这种概念，
补丁只能靠「放一个新包、用 `!` 前缀压过旧包」，于是同一个资源在磁盘上存了 2~5 份，
最大的单例 `monstercard_image.img` 光冗余就 40 MB。

### 2.5 其他

| 项 | 实测值 / 现状 | 现代做法 |
| --- | --- | --- |
| 小图数量 | **66% 的帧 ≤ 256 像素**（但只占 1.3% 的像素字节） | 打进 **atlas**，合批 → draw call 从「每图一次」降到「每图集一次」 |
| 包体积分布 | 中位 **0.56 MB**，最大 **600 MB**，46 个包 >100 MB | chunk 化后可以按需下载、断点续传、并行 |
| 完整性校验 | SHA-256 只覆盖「头+索引」的 `len//17*17` 字节（启发式截断） | per-chunk hash + Merkle 树 → 可校验任意片段、支持 P2P/续传 |
| 文件名「加密」 | 固定密钥 XOR，密钥在公开资料里到处都是 | 不做伪加密；要防篡改就上 **Ed25519 签名** |
| 引擎生态 | Unity / UE / Godot 都不认 NPK，每个团队都得自己写解包器（本仓库就写了 3 个） | Addressables / IoStore / `.pck` 都是引擎原生支持 |
| 2D 表现方式 | 逐帧大图，**2877 万帧** | Spine / DragonBones 骨骼动画，或矢量 UI；帧数能降 1~2 个数量级 |

## 3. 现代对应技术：按问题映射

| NPK 的问题 | 今天的解法 | 代表实现 |
| --- | --- | --- |
| TOC 与数据混在一个文件、全量读索引 | **TOC 分离 + chunk 化 + mmap** | UE **IoStore**（`.utoc` 目录 / `.ucas` 数据）、Unity **Addressables / AssetBundle**（LZ4 chunk）、Godot 4 `.pck`、Cocos Creator AssetBundle |
| 2880 万个独立 zlib 流 | **zstd + 训练字典**（大块更好），热路径用 **LZ4** | zstd `--train`；Oodle（UE 商用） |
| 无去重、补丁整包替换 | **内容定义分块（FastCDC）+ CAS + catalog 版本** | AAA live-service 的标准做法；增量补丁用 `zstd --patch-from` / xdelta / bsdiff |
| 4B/px 未压缩驻留显存 | **BC7 / ASTC / KTX2-BasisU**（GPU 原生可采样） | 移动端 ASTC、PC 端 BC7、跨平台 BasisU |
| 每张小图一个纹理 | **sprite atlas + 合批** | TexturePacker、Spine atlas、Unity Sprite Atlas |
| 索引 264B 定长 | **hash 表 + 字符串池**（8B hash 查表，名字只存一份） | 所有现代 pak 格式 |
| 校验只覆盖前缀 | **per-chunk SHA-256 + Merkle root + 签名** | Steam Depot / 现代 launcher |
| 逐帧 2D 动画 | **骨骼动画 / 矢量** | Spine、DragonBones、Rive |

如果要重做一个同类 2D 游戏，今天的默认答案基本是：
**引擎原生 pak（Addressables 或 IoStore）+ zstd + atlas + ASTC/BC7 + 骨骼动画**，
不会有团队再从零发明一个「索引 + 每帧 zlib」的私有容器。

## 4. 关键判断：磁盘不是瓶颈，加载与显存才是

实测把账算清楚后，结论会和直觉相反：

| 改造方向 | 对**磁盘体积**的影响 | 对**运行时**的影响 |
| --- | --- | --- |
| zstd 字典 + 跨包去重 | 28.5 GB → 约 24 GB（**-15%**，有限） | 无 |
| 换 BC7/ASTC | **持平甚至变大**（长零串被打散） | 显存 **÷4**，免 CPU 解压，**收益大** |
| atlas 合批 | 略小 | draw call / 状态切换大幅下降，**收益最大** |
| 补丁 chunk 化 | 基本不变 | 热更从「整 img / 整包」变成「按 chunk」，**收益大** |
| 索引瘦身 | -40 MB（可忽略） | 加载期少解析 55.8 MB，**收益小** |

所以如果只能做一件事，**先做 atlas 合批**；如果做两件，再加 **VRAM 压缩格式**；
容器和补丁系统的重构排在这两件**之后**——它解决的是运维问题（热更成本），不是帧率。

## 5. 两条落地的路

### 5.1 只是维护这个老客户端 → 不动运行时格式，只改分发层

1. **保持 NPK 作为运行时格式**（客户端和工具链全绑死，重做成本远大于收益）；
2. 在 CDN 侧做一次 **repack**：内容定义分块 + zstd + Merkle 清单，
   首次安装后落地成本地 NPK（离线转换），更新只下变化 chunk；
3. 这套解析能力本仓库已经有了（`tools/npk_parser.py` / `npk_hexwalk.py` / `npk_v1_walk.py`，
   全语料校验过 4,730 个包），做离线 repack 不需要新的逆向工作；
4. 顺手清掉 0.3 GB 完全重复的包、1.88 GB 同名冗余——这些是**补丁文化**的产物，不是格式的锅。

### 5.2 要做新项目 → 不要发明新 NPK

直接用引擎原生方案（Addressables / IoStore / `.pck`），2D 走 atlas + 骨骼动画。
私有格式唯一能换来的是「不被通用工具解析」这种伪安全，代价是每个工具都要自己写。
